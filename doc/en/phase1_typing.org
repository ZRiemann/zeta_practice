* Goal

=Phase 1= should deliver the first complete usable loop:

#+begin_src text
open Web app
  -> authenticate
  -> start typing practice
  -> practice locally in browser
  -> finish and submit result
  -> persist result
  -> update statistics/profile
  -> generate the next practice from current ability
#+end_src

The typing module is a practice system, not a basic keyboard tutorial.
It assumes key positions, finger usage, posture, and other fundamentals are
taught externally.

* Explicit Non-goals

Do not include in Phase 1:

- key-position or finger-placement lessons;
- curriculum trees, mastery graphs, or lesson unlock systems;
- game economies, leaderboards, social features, or achievements;
- AI tutors or model-based recommendation;
- offline synchronization;
- PostgreSQL, Redis, queues, or microservices;
- complex parent-management/RBAC workflows.

** Persistence model

Implement only what the typing loop requires.

Initial conceptual tables:

#+begin_src text
users
user_settings
auth_sessions
typing_sessions
typing_session_char_stats
typing_profiles
#+end_src

=users= stores identity and password hash, never plaintext passwords.
=auth_sessions= stores revocable server-side login sessions.
=typing_sessions= stores one completed practice summary.
=typing_session_char_stats= stores per-session character attempts/errors so
recent weakness can be computed without storing every raw keystroke.
=typing_profiles= stores the current small adaptive state.

Use explicit schema migrations from the first database version.

** Domain and metrics

Initial practice types:

1. mixed lowercase/uppercase letters;
2. comprehensive characters with numbers/basic punctuation according to difficulty;
3. words;
4. short sentences.

The browser receives one =PracticeSpec= and runs the complete keyboard loop
locally.

Recommended domain concepts:

#+begin_src rust
PracticeType
PracticeSpec
PracticeResult
CharacterStat
TypingProfile
Difficulty
#+end_src

Do not expose Dioxus component state as the domain model.

*** Metric contract

Define the metrics before implementing UI:

- =duration_ms=: monotonic active practice duration;
- =attempt_count=: printable typing attempts considered by the session model;
- =correct_count=: attempts correct under the chosen cursor/correction semantics;
- =error_count=: incorrect attempts;
- =accuracy=: =correct_count / attempt_count= when attempts are non-zero;
- =completed_characters=: target characters successfully completed;
- =wpm=: =(completed_characters / 5) / active_minutes=;
- =correction_count=: correction actions tracked separately when supported.

The exact wrong-key/backspace cursor behavior must be fixed in tests and remain
stable across UI refactors.

Use a browser monotonic timer for active-session timing. Wall-clock timestamps
are for persistence/audit, not WPM measurement.

** Adaptive policy

Keep the first algorithm deterministic and explainable.

Maintain a small profile such as:

#+begin_src text
recent_accuracy
recent_wpm
difficulty
weak_characters
last_practiced_at
#+end_src

Use a bounded recent window rather than allowing very old practice to dominate
the weakness calculation.

Initial adaptive policy may use centralized defaults such as:

#+begin_src text
accuracy >= 95% for a stable recent window -> consider increasing difficulty
accuracy < 85%                         -> reduce complexity or reinforce weakness
otherwise                              -> retain difficulty
#+end_src

For generated character practice, bias a bounded share of content toward weak
characters; for example, a default 70/30 normal-to-weak weighting. These are
configuration/policy constants, not UI magic numbers.

WPM is a secondary progression signal. Early improvement should not reward
speed at the cost of persistently poor accuracy.

** Content ownership

Keep content ownership simple:

#+begin_src text
assets/
  typing/
    en-US/
      words.*
      sentences.*
#+end_src

Generated character practice is produced from =PracticeSpec + TypingProfile=.
Word/sentence practice selects from versioned repository content and may prefer
items containing current weak characters.

Do not introduce a curriculum database in Phase 1.

** UI boundaries

Keep the typing page intentionally small:

#+begin_src text
+--------------------------------------+
| Practice type / progress             |
+--------------------------------------+
|                                      |
|              Target text             |
|              User input              |
|                                      |
+--------------------------------------+
| Accuracy       WPM        Time        |
+--------------------------------------+
| Progress / concise adaptive hint     |
+--------------------------------------+
#+end_src

No virtual keyboard, finger animation, key-position lessons, or game UI is
required.

The summary view should answer:

- how did this session perform?
- which characters were weak?
- what should be practiced next?

** Server API boundary

Use typed Dioxus server/client boundaries from the forge-managed framework
version. Avoid inventing a second REST API unless a demonstrated non-Dioxus
client requires it.

The minimum operations are conceptually:

#+begin_src text
login / logout / current_user
start_practice
submit_practice_result
recent_typing_history
typing_profile
#+end_src

=start_practice= returns a bounded practice specification/content payload.
=submit_practice_result= accepts a completed summary and per-character counts,
not a network call per keystroke and not an unbounded raw event stream.

Server input must validate ownership, count relationships, payload limits, and
supported practice/difficulty values before persistence.

* Verification

Focused automated coverage should include:

- generator determinism with fixed seeds where randomness is used;
- target matching and correction semantics;
- zero-duration/zero-attempt safety;
- Accuracy and WPM calculations;
- per-character error accounting;
- adaptive threshold transitions;
- weak-character weighting bounds;
- authentication isolation;
- SQLite migration and restart persistence;
- server payload validation;
- bilingual route/component smoke tests.

Use =zeta_forge= Rust entrypoints for doctor, metadata, check, build, and test.
Do not claim Web runtime validation until the application has actually been run
in a browser.

* Phase acceptance

=Phase 1= is complete when two independent users can use the Web application,
complete typing practices without keystroke network round trips, persist their
own history, see Accuracy/WPM/error statistics, and receive a deterministic
next-practice adjustment based on recent performance.

A second practice module is not part of this Phase.

Stage 1.12 records integration evidence. All preceding Stages and the full loop
must pass their required checks before Phase acceptance. If the final Stage
and Phase are versioned together, record both in one delivery.
