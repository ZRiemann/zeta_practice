* 范围

本文定义首阶段架构边界。目标是在保证多用户 Web 练习可靠性的前提下保持系统足够小，
同时为以后增加新的练习模块保留清晰边界。

* 系统形态

首阶段采用单一可部署应用：

#+begin_src text
Browser
  |
  | HTTPS
  v
zeta_practice
  |- Dioxus Web UI / 浏览器本地练习状态
  |- 认证和 session
  |- application services
  |- typing 模块
  |- persistence/repositories
  v
持久化存储上的 SQLite
#+end_src

首阶段不把 frontend、backend、auth、statistics 或 typing 拆成独立网络服务。

主机初始化、反向代理、证书、服务部署和运维属于 =zsa=。本仓库负责应用运行契约，
后续实现时负责应用构建产物和容器定义。

* Client / Server 边界

** 浏览器负责低延迟交互

typing 的键盘事件、目标字符匹配、耗时测量、当前进度以及实时 Accuracy/WPM 都在浏览器
本地执行。

禁止每次按键都请求服务端。

典型流程：

#+begin_src text
server -> 练习规格/内容 -> browser
browser -> 本地 typing loop -> result summary
browser -> 完成结果 -> server
server -> 保存历史 -> 更新统计/profile
#+end_src

因此短暂网络波动不会改变打字响应延迟。最终提交失败时应允许重试，但 Phase 1 不实现
完整 offline-sync 引擎。

** 服务端负责权威账户和持久状态

服务端负责：

- 用户身份和认证；
- 服务端登录 session；
- 持久化练习历史；
- 用户长期统计；
- adaptive profile 状态和下一次练习策略输入；
- 数据库 migration 和边界校验。

浏览器不能直接访问 SQLite。

* 练习模块边界

应用壳只负责稳定的跨模块能力：

- routing 和顶层导航；
- 当前用户与认证；
- 国际化；
- 应用配置；
- 持久化基础设施。

=typing= 模块负责：

- 练习类型以及静态/动态内容；
- typing session 语义；
- Accuracy/WPM/error 定义；
- 字符弱项统计；
- typing profile 与 adaptive 规则；
- typing 专属 UI。

Phase 1 不建立通用 =practice_core::skill/mastery/curriculum= 框架。只有第二个真实模块
出现并证明存在相同职责后，才提取共享能力。

* 认证与用户模型

首阶段支持多用户密码认证。

密码不得明文保存。正式实现使用经过审查的密码哈希算法（例如 Argon2id）以及服务端
session。HTTPS 部署时浏览器认证 Cookie 应合理配置 =HttpOnly=、=Secure= 和 =SameSite=。

角色模型保持最小。未来可以增加 Parent/Admin 管理 Student 账户和查看统计，但 Phase 1
不引入大型 RBAC 框架。

* 国际化

UI locale 与练习内容语言分离。例如可以使用中文 UI，同时练习英文 typing 内容。

初始 UI：

- =zh-CN=
- =en-US=

用户可见字符串不能散落硬编码在领域逻辑中。

* 持久化

首阶段数据库使用服务端 SQLite。

原因：

- 初始负载很小；
- 单实例服务足够；
- 部署和备份简单；
- 通过 storage/repository 边界，未来迁移数据库不需要改写 typing 领域规则。

SQLite 文件必须位于持久化存储，不能依赖临时 container filesystem。

PostgreSQL、Redis、分布式缓存、消息队列和多节点数据库协调均不属于首阶段。

* Rust 与第三方依赖治理

=zeta_forge= 是 ZetaX Rust toolchain 和公共第三方 Rust 依赖版本的统一权威来源。

业务仓库通过根目录 =zeta-rust.toml= 声明 Forge 批准的工具链和
=dioxus-web-fullstack= 能力。本仓库拥有自己的 Rust 源码、workspace 成员、业务
feature 组合和提交到仓库的 =Cargo.lock=。workspace member 通过 =workspace = true=
继承直接依赖，workspace 只能选择 Forge 目录批准的精确版本与来源。

Cargo 仍然负责 Rust 依赖解析和构建，但不是 ZetaX 的独立依赖治理来源。

如果需要的公共 crate 或工具版本尚未进入 =zeta_forge=，必须先批准目录条目并验证。
普通业务 feature 由项目组合；=rusqlite/bundled= 等明确约束仍由 Forge 检查。

Forge 批准 Dioxus 0.7.10，并在选择 =dioxus-web-fullstack= 能力时检查匹配版本的
Dioxus CLI 与 Web Rust target。应用拥有自己的
=web= 和 =server= feature 组合。

* 演进原则

- 单应用、单数据库能满足需求时不增加分布式复杂度。
- typing 核心领域逻辑尽量可以脱离浏览器和数据库独立测试。
- Dioxus renderer 细节保持在 UI 外层。
- 外部表示和持久化 record 不进入核心 typing 计算。
- 只为已经证明存在的变化建立扩展点。
- 数据库 schema 变更必须显式 migration 并同步文档。
